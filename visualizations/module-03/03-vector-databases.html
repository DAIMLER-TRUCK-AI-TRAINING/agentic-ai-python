Topic 3

Exact, fast or cheap: pick two, then pick where it runs

A vector index answers one question: which stored vectors are nearest to this query vector? A flat index checks every vector and is always right; IVF and HNSW check a fraction and are usually right. Search the map with each index and turn the knobs until recall drops. Then switch between FAISS, Chroma and Pinecone, add a region = EU filter, and see how each one handles it.

Index types

  

    

      
IndexHow it searchesKnobTrade-off

      
        
FlatCompares the query with every vectornoneExact; cost grows linearly. Fine up to hundreds of thousands of vectors.

        
IVFClusters vectors into cells (k-means), then scans only the cells nearest the querynlist cells, nprobe cells searchedNeeds a training step; misses neighbours that sit just across a cell border.

        
HNSWWalks a layered graph: sparse upper layers route between regions, the bottom layer links near neighboursM links per node, efSearch beam widthFast and high recall; more memory for the links; deletes are awkward.

Engineering takeaway: measure recall@k against a flat index on your own queries before you tune
    anything. At 36 vectors every index is fast; the knobs matter at millions, and the price of a wrong knob is silent: the right chunk
    is never retrieved, and the answer looks fine.

  
Common trap: treating the vector store as harmless because it “only holds numbers”. Stores keep the
    chunk text and metadata next to the vectors, and embeddings themselves can leak content. Classify the store like the source
    documents: access control, encryption and data residency apply (Module 5).
