Topic 5

Keywords find codes, vectors find meaning, metadata finds the right version

Each retrieval method fails a different kind of query. BM25 keyword search nails an exact error code and misses a paraphrase; vector search does the opposite; and neither can tell a current policy from a superseded one. Run all three queries in each mode, fuse the lists with reciprocal rank fusion, add a cross-encoder re-ranker, then switch on the metadata filters.

Which method catches which query

  

    

      
MethodStrong atWeak at

      
        
BM25 (keyword)Exact IDs, error codes, product names, rare termsSynonyms, paraphrases, other languages, spelling variants (“wifi” vs “Wi-Fi”)

        
VectorMeaning, paraphrases, multilingual questionsCodes and IDs that carry little meaning (“PAY-17”), negation, exact numbers

        
Hybrid (RRF)Robust across both: a document ranked well by either list risesCannot invent a document neither list found; two weak signals stay weak

        
Re-ranker (cross-encoder)Reading query and passage together to reorder the top 20–50Cost and latency per candidate; cannot see dates, versions or permissions

        
Metadata filterHard rules: version, region, document type, accessOnly as good as the metadata you captured at ingestion

      
    

  

  
Engineering takeaway: run hybrid retrieval by default, re-rank a short candidate list, and express every
    hard rule (version, region, permission) as a metadata filter rather than hoping relevance will get it right. Relevance ranking
    answers “which text matches?”; only metadata answers “which text is allowed and in force?”.

  
Common trap: filtering by permission after generation, or in the prompt (“only use documents
    the user may see”). The model has already read the contract by then. Apply access filters in the retrieval query, so restricted
    chunks never reach the prompt.
