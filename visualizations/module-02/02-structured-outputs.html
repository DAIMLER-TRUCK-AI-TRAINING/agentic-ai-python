Valid JSON is not a valid answer

Structured outputs make the model’s reply match your schema, but a schema checks shape, not truth. Build the ChangeRequest schema for change CHG-20932, choose between asking for JSON in the prompt and strict schema enforcement, then press Run all ▶ to push five model outputs through the parse, schema and business-rule gates. Engineering takeaway: strict schemas move failures from “unparseable” to “parseable but wrong”. That is
    progress only if gate 3 exists. Keep the raw output with every record, send validation errors back for one retry, assert on
    structure in tests, and route business-rule failures to a person rather than into the change database.

  
Common trap: a required, non-nullable field for data that may be absent. CHG-20932 is a
    pre-approved standard change with no rollback section. Under strict enforcement a rollback_plan: str field must be
    filled, so the model writes a plausible plan, and the schema happily accepts it. Make it str | None, tell the model to use
    null for anything the document does not state, and check that any value you keep appears in the source.
