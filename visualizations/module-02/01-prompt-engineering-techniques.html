Same tickets, same model, four prompts: different answers and a different bill

A prompt is code: each technique changes accuracy, latency and what you pay on every call. Switch the triage prompt between zero-shot, few-shot and chain-of-thought, add a role with label definitions, and compare OpenAI with Claude on ten labelled tickets. Then plant a template bug and work out the cause from the symptoms alone.

Four techniques, four cost drivers

  

    

      
TechniqueWhat you addCost driverHelps whenWatch out for

      
        
Zero-shotThe task and the label setShortest promptLabels are self-explanatoryThe model’s conventions are not your team’s (VPN credential errors, lockouts)

        
Few-shot3–5 labelled examplesExamples are resent on every call (cache them: Topic 5)House conventions, edge cases, exact output formatSkewed or stale examples bias every prediction

TemplateOne template renders the text for both; only where each part is placed differs. Version it like code.

      
    

  

  
Outline vs current API: the outline’s “chain-of-thought” is still taught as a prompt, and it still helps on
    models run without reasoning. Current reasoning models already think before answering, so asking them to “think step by step”
    mostly duplicates paid output tokens. Raise reasoning.effort (OpenAI) or output_config.effort (Claude) instead,
    and keep your final answer in a separate, parseable field.


  
Prompt debugging: from symptom to cause

  

    

      
Symptom on the labelled setLikely causeDebug step

      
        
Labels outside the allowed set (network_incident)A template variable rendered from a stale listPrint the rendered prompt; generate {labels} from the same enum the parser validates against

        
Prose instead of a labelOutput format not pinned, or CoT with no answer linePin the format, or use structured outputs (Topic 2)

        
One class over-predictedFew-shot examples all from one classBalance the examples; read the confusion matrix, not just accuracy

        
A fix for one ticket breaks anotherNo regression setScore every prompt change on the full labelled set, on both providers

      
    

  

  
Common trap: tuning the prompt on the one ticket a user complained about. Every change here moves
    several rows at once, sometimes in opposite directions. Keep a labelled set, version your prompts, and accept a change only when
    the whole set improves on the provider you ship.
