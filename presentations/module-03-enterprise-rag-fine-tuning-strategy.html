Topic 1 · RAG fundamentals

RAG is search plus generation: the answer can only cite what retrieval returned

# Claude · chunks as search_result blocks, native citations content = [{"type": "search_result", "source": h.metadata["doc_id"], "title": h.metadata["title"], "citations": {"enabled": True}, "content": [{"type": "text", "text": h.page_content}]} for h in hits] + [{"type": "text", "text": question}] msg = claude.messages.create(model=ANTHROPIC_MODEL, max_tokens=4096, messages=[{"role": "user", "content": content}]) cited = {c.source for b in msg.content if b.type == "text" for c in b.citations or []} assert cited <= {h.metadata["doc_id"] for h in hits}
# OpenAI · no citation type for your chunks: cite through the schema class GroundedAnswer(BaseModel): answerable: bool # False if the sources do not answer it answer: str cited_ids: list[str] # only ids that appear in <sources> r = oai.responses.parse(model=OPENAI_MODEL, text_format=GroundedAnswer, input=f"<sources>\n{format_sources(hits)}\n</sources>\n\n{question}") a = r.output_parsed assert set(a.cited_ids) <= {h.metadata["doc_id"] for h in hits}
RAG has two halves. Ingest runs offline: load, chunk, embed, index. Query runs per question: retrieve the best chunks, put them in the prompt, and generate an answer that cites them. Bridge: it is a search index in front of a generator, so most RAG quality work is search quality work. Every box is a decision you own and measure today. The two panes show grounded, cited answers on both SDKs. Claude takes your chunks as search_result blocks and returns citations on the text; OpenAI has no citation type for your own chunks, so you cite through a schema field. Either way your code checks that every cited ID was actually retrieved. One trap from the guide's dry runs: Claude citations and structured outputs do not combine, so if you need a typed answer and checked sources, use the schema pattern on both providers. Topic 1 · RAG fundamentals

Most RAG failures are retrieval failures, and each one has a known fix

Common trap: "The model has a 1M-token context, so we don't need retrieval." Answer quality degrades with very long inputs, the bill scales with every question, and one shared prompt cannot apply per-user access rules.
Walk the failures left to right, because they are the agenda for the rest of the morning. Five of the seven happen before the model sees anything: vector search misses exact identifiers such as CHG-20931, keyword search misses paraphrases such as "my machine wants a long number before Windows starts", a fixed-size chunk splits the SLA table from its heading, a retired policy keeps answering because the delete never propagated, and a customer sees an internal runbook because filtering came after ranking. Each has a fix you build today. The two generation failures are a blended answer when sources disagree, and indirect prompt injection, where a document says "ignore your instructions"; treat sources as data, and Module 5 adds the guardrails. Topic 2 · Fine-tuning overview & decision framework overview level

Fine-tuning changes the weights, and in 2026 that means a model you host

PlatformFine-tuning in 2026 (checked 28–29 October)Consequence
OpenAI fine-tuning APIWinding down: closed to new organisations on 7 May 2026, to organisations without recent fine-tuned inference on 2 July 2026, and to everyone on 6 January 2027. Fine-tuned models serve until their base model is retiredNo new work on it; its methods remain useful vocabulary

Fine-tuning continues training a pretrained model on your examples, so that the behaviour you want becomes the default rather than something you ask for in every prompt. Full fine-tuning trains every weight and is mostly for model builders. LoRA learns a low-rank update beside each frozen matrix: on the SmolLM2-135M model from Module 1, rank 16 on the attention projections trains 1.35% of the weights, so the adapter is megabytes and one base model can serve several. QLoRA does the same on a 4-bit base, and instruction tuning is how chat models are made: you consume it rather than do it. The provider picture changed in 2026: OpenAI is winding its fine-tuning API down, the Claude API has never offered it, and Bedrock's only fine-tunable Claude model is retired. For the course's default model families the levers are prompts, retrieval and tools; fine-tuning means an open-weight model you host. Topic 2 · Fine-tuning overview & decision framework workshop · 30 min · from the delivery schedule

Choose by the gap: knowledge goes in an index, behaviour in prompts, weights last

CriterionPrompt engineeringRAGFine-tuningHybrid
Data you needA few examplesThe documents, with metadataHundreds to thousands of labelled examplesBoth
LatencyModel call onlyPlus retrieval and a longer promptLowest when a small tuned model replaces a large oneRetrieval plus a small model
CostTokens per callIndex, storage, chunk tokensTraining, hosting, retrainingHighest to build
Update frequencyEdit the promptRe-index changed documents in minutesRetrain for each changeFacts via RAG, behaviour via training
Provenance—Cite and delete per documentIn the weights: no citation, no deletionFacts stay citable
The outline's criteria are data availability, latency, cost and update frequency, but ask one question first because it settles most cases: is the gap knowledge, where the model does not know your facts, or behaviour, where it knows enough but does not act the way you need? Knowledge belongs in an index you can update, cite and delete from. A small, stable corpus can simply ride in the prompt: stuffing 800,000 tokens costs about $3.20 a question on Claude Opus 5.5, or $0.16 if every token is a cache read, against roughly $0.002 for four retrieved chunks; and 5,000 KB articles at 500 tokens each will not fit a 1M-token window at all. Research agrees that RAG beats fine-tuning for injecting knowledge; RAFT is the hybrid that trains a model to use retrieved documents well. The workshop comes from the delivery schedule rather than the hands-on list: teams fill the fine-tuning decision canvas for four scenarios and present one decision with the evaluation that would overturn it. Topic 3 · Vector databases

Vector search is approximate nearest neighbours: pick a library, a database or a service

FAISSChromaPinecone
What it isA similarity-search libraryAn open-source database, embedded or as a serverA managed, serverless service
PersistenceYou save and load index filesBuilt in (PersistentClient)Managed
Metadata filteringNone: keep IDs and metadata yourselfwhere on metadata, where_document on textMetadata filters
Updates and deletesLimited by index type; often rebuildUpsert and delete by IDUpsert and delete by ID; namespaces
Data residencyWherever you run itWherever you run itThe provider's cloud regions
In this courseLabs (faiss-cpu 1.15.1)Labs (chromadb 1.5.9)Trade-offs only; not in the outline's tools
A vector database stores one embedding per chunk and answers "which stored vectors are nearest to this one?" quickly, and usually approximately. The animation is HNSW, the default in most vector databases: a greedy walk down a layered graph, with ef trading recall for speed. Flat search is exact and is your ground truth when you tune ef or nprobe; IVF and product quantisation matter at much larger scale. The course's embeddings are unit length, so cosine similarity equals the inner product: pick one metric per index, and store the embedding model's ID with it, because mixing models in one index silently breaks search. Then make the operational choice: FAISS is a library, Chroma a database you run, Pinecone a service. Residency, deletes and filtering decide before any benchmark does; indexes are derived data and follow their sources' retention rules. Ask: when a document is deleted at the source, how long may its chunks stay searchable?

A chunk is the unit you retrieve, cite and pay for. Too small and it loses the context that gives it meaning, such as "restore within 4 hours" without saying which contract; too large and it mixes topics, its embedding blurs, and it fills the prompt with text the question did not need. Read it before you crown a winner: precision is counted per chunk against relevant documents, so tiny chunks win simply because four slivers of the right document fill the top 4, and the 64-token winner is too small to answer from. Topic 5 · Metadata design & hybrid retrieval

Metadata is access control: filter before you rank, from the caller's identity

Filter before ranking

A post-filter takes the top 4 and then drops what the caller may not see, which can leave nothing relevant.

Access comes from the caller, never the model

The model may choose doc_type; it never chooses region or audience. Module 5 builds this as access control.

A filter always returns something

The US analyst still gets four chunks. Allow "not in the sources", and add a score floor.

Context helps the embedding

Prepending chunk context cut top-20 retrieval failures by 35% in Anthropic's experiments; 67% with contextual BM25 and re-ranking.

Metadata is how retrieval knows who may see a chunk, how fresh it is and what to cite: doc_id and title for citations and deletes, doc_type for routing, audience and region for access and residency, and access lists such as the allowed group IDs the SharePoint reader captures. Filter before ranking. The three rows are representative output from the guide for one question: the EU analyst gets the contract; the US analyst sees neither EU-only contract yet still receives four chunks, none of which answers; the customer sees only customer articles. A filter always returns something, so the generator must be allowed to say "not in the sources", and retrieval needs a score floor calibrated on labelled queries. Access filters come from the authenticated caller, never from the question or the model. Ask: in your estate, where would the access list for a document come from?
Topic 5 · Metadata design & hybrid retrieval

Keywords find identifiers, vectors find meaning: fuse the rankings, then re-rank

# Hybrid retrieval: reciprocal rank fusion over the vector and BM25 rankings, then a cross-encoder def hybrid_search(query: str, k: int = 4, pool: int = 10) -> list[Document]: fused: dict[tuple, list] = {} for ranking in (store.similarity_search(query, k=pool), keyword_search(query, k=pool)): for rank, chunk in enumerate(ranking, 1): key = (chunk.metadata["doc_id"], chunk.metadata["start_index"]) fused.setdefault(key, [0.0, chunk])[0] += 1 / (60 + rank) # ranks, not scores: no calibration needed return [chunk for _, chunk in sorted(fused.values(), key=lambda e: -e[0])][:k] reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2") # local and fast, but English-only def rerank(query: str, candidates: list[Document], k: int = 4) -> list[Document]: scores = reranker.predict([(query, c.page_content) for c in candidates]) return [c for _, c in sorted(zip(scores, candidates), key=lambda p: -p[0])][:k]
Vector search matches meaning; keyword search matches exact tokens such as CHG-20931, error codes and host names, and BM25 is a strong baseline across domains. Hybrid retrieval runs both and fuses the rankings with reciprocal rank fusion, which needs only ranks, not comparable scores. Do the arithmetic on the slide: a chunk that is third in both lists beats one that is second in only one. That is exactly how the guide's dry run fixed the CHG-20931 query and lost the "my own iPad" query at the same time; re-ranking a pool of 10 with a cross-encoder recovered both. A cross-encoder reads query and chunk together, so it is accurate but too slow for the whole index: it only re-orders candidates. The local model is English-only, so check multilingual tickets. One more trap: quote every term before you pass user text to an FTS5 MATCH, or "AND" and "NEAR" change the meaning. Ask: which queries in your support logs are mostly identifiers?

Build the same pipeline twice and the frameworks show their centres of gravity. LlamaIndex is built around the data side: readers, node parsers, indexes and query engines, with hierarchical documents and advanced retrieval built in. LangChain is built around composition: chains, agents, middleware and tools, and Module 4's LangGraph. Use LlamaIndex when the hard part is the data, LangChain when the hard part is the application; they interoperate, and any retriever can sit behind a LangChain tool. Two traps from the dry runs: chunk_size means characters in one library and tokens in the other, and LlamaIndex's default query engine does not ask for citations, so the user sees uncited prose unless you pass your own prompt. Both outline names have moved: langchain-community was sunset in May and warns on import, and the Hub is now a catalogue of llama-index-readers packages. In Lab 01 you rebuild the pipeline in LlamaIndex and record your verdict. Ask: which half of your RAG system do you expect to be harder?

A connector authenticates as a service identity, pulls changes incrementally from a stored checkpoint, carries each document's access list, and propagates deletions; without that last step the index keeps answering from documents that no longer exist. Use an app registration or service account with read-only, least-privilege scopes, never a person's token. Topic 9 · Agentic RAG

Agentic RAG makes retrieval a tool: the agent decides when and what to search

Task (representative trace, three dry runs)OpenAIClaude
"Thanks, that fixed it!"0 searches0 searches
"The VPN keeps rejecting my new password."1 search, a keyword-stuffed query1 search: "VPN rejects new password troubleshooting"
Firmware upgrade + P1 restore time1 search covering both parts2 searches, the second with doc_type="contract"
Assert onThe tool was called, cited IDs came from the tool, and the facts: never on search counts
So far every question triggered retrieval: LangChain calls that 2-step RAG, and it is predictable and cheap, but wasteful for "thanks, that fixed it". In agentic RAG the retriever is a tool, search_knowledge, with Module 2's tool contract: narrow input, concise JSON with stable IDs, and an actionable message when nothing is found. The agent decides whether to search, for what, in which doc_type, and whether to search again. In the dry runs both providers skipped search for thanks, and both answered the two-document question correctly by different routes, so assert on outcomes, not on search counts. The right-hand loop is corrective retrieval, and its last two states are the knowledge-management half of the topic: every question the assistant cannot answer is a gap in the knowledge base, so log it and route recurring gaps to the owning team. Give the agent a search budget, and if it does not beat the fixed pipeline on your labelled queries, ship the fixed pipeline. Module 4 turns this loop into an explicit LangGraph pattern. Wrap-up

Key takeaways, and a quick self-check

01Retrieval is the ceiling

The answer can only cite what retrieval returned. Measure retrieval first, then the answers.

02Choose by the gap

Knowledge goes in an index; behaviour in prompts. In 2026, fine-tuning means open weights you host.
