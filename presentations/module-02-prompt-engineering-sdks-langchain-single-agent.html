Topic 1 · Prompt engineering: techniques, templates & debugging

A prompt is code: template it, version it, debug it against a test set

Read the rendered prompt, not the template

Most "it ignored my rule" bugs are a variable that rendered empty, twice or in the wrong place. Log the exact request.

Classify before you fix

Ambiguous rule, missing definition, skewed examples, format drift, or information the ticket simply does not contain.

One change per run, on the whole set

A tweak that fixes INC-104237 can break three other tickets. The labelled set is your regression suite.

Version prompts like code

triage-v4 lives in git, in the trace metadata and in the eval report, so every output points back to its prompt.

A template is a function: typed inputs, one rendered output. Keep the template in version control, give it a name and a version, and record that version on every call, so a bad label can be traced to the exact prompt that produced it. When a ticket fails, resist editing the wording straight away. First read the rendered request from the trace: is the examples block empty, is the ticket truncated, did a rule render twice? Then classify the failure, change one thing, and rerun the whole labelled set, because prompt fixes regress like code fixes. The pass and fail marks here are illustrative; in Lab 01 you produce real ones. LangChain's ChatPromptTemplate, which you meet on slide 12, is the same idea with message roles built in. Ask: who reviews a prompt change in your team today, and against what?

There are three layers, and engineers tend to stop at the first. Asking for JSON in the prompt is a request. Schema enforcement through structured outputs is a guarantee about shape: during decoding the model cannot pick a token that breaks the schema. Validation in your code is where truth gets checked: Pydantic for types and enums, then the business rules only you know, such as whether KB-0450 exists and belongs to the team the model chose. Both SDKs take the same Pydantic class, so one schema drives both providers. Check the stop condition before you parse: a refusal or a truncated response is not a malformed object. And remember Module 1 Lab 02: a field that cannot say "unknown" forces the model to invent a value, so make it Optional. In Lab 01 Part 2 you enforce the schema on document extraction with both SDKs. Both APIs are the same RPC with different field names, so learn the mapping once and you can read either codebase. OpenAI's primary path is now the Responses API; much existing code still calls Chat Completions, client.chat.completions.create with a messages list, so expect to meet it. Two differences matter in design reviews. State: Claude is stateless, so you own the history; OpenAI can hold it server-side through previous_response_id, which is convenient but moves conversation data to the provider. Output cap: Claude requires max_tokens on every call. Streaming does not change the contract, only the delivery: text arrives as deltas from the first token, and the stop reason and usage arrive last, so log usage from the final event. Model IDs come from .env, never from code; both are the defaults verified on 27 October 2026. Ask: where should conversation state live in your architecture, with you or with the provider?
Topic 3 · OpenAI SDK and Claude SDK, side by side

Tool calling: the model asks, your code executes

# OpenAI Responses API · function calling tools = [{"type": "function", "name": "lookup_kb", "description": KB_DOC, "parameters": KB_SCHEMA, "strict": True}] r = client.responses.create(model=OPENAI_MODEL, input=items, tools=tools) items += r.output # keep the call (and reasoning) items for c in r.output: if c.type == "function_call": hits = lookup_kb(**json.loads(c.arguments)) # a JSON string items.append({"type": "function_call_output", "call_id": c.call_id, "output": json.dumps(hits)}) r = client.responses.create(model=OPENAI_MODEL, input=items, tools=tools)
# Claude Messages API · tool use tools = [{"name": "lookup_kb", "description": KB_DOC, "input_schema": KB_SCHEMA}] m = client.messages.create(model=ANTHROPIC_MODEL, max_tokens=16000, messages=msgs, tools=tools) msgs.append({"role": "assistant", "content": m.content}) if m.stop_reason == "tool_use": msgs.append({"role": "user", "content": [ {"type": "tool_result", "tool_use_id": b.id, "content": json.dumps(lookup_kb(**b.input))} # already a dict for b in m.content if b.type == "tool_use"]}) # … then call messages.create again with msgs
This is the slide to slow down on. A tool definition is an RPC contract: a name, a description the model reads as instructions, and a JSON Schema for the arguments. The model never executes anything. It returns a request, a function_call item or a tool_use block, and stops. Your code validates the arguments, runs the function inside your trust boundary, and sends the result back tagged with the same ID: call_id on OpenAI, tool_use_id on Claude. Get the ID wrong and the API rejects the turn. Note the small asymmetries: OpenAI's arguments arrive as a JSON string, Claude's input as a dict; OpenAI wants the call items echoed back, and Claude wants the whole assistant turn appended. Either model may ask for several calls in one turn. In Lab 02 you build this loop with the OpenAI SDK, rebuild it with Claude, and record both in the agent trace sheet. Ask: what would your code do if the model asked for a tool you never offered?
Topic 4 · Agent Skills & OpenSpec agent design overview · 20-min walkthrough

A Skill is a procedure on disk that loads only when the task needs it

System prompt

Rules for every request. Always in context, always paid for.

Skill

A repeated procedure with its references and scripts. Only its name and description load until it is needed.

Tool

One action with a typed contract, as on slide 7. The model asks; your code runs it.

MCP server · Module 4

A standard plug that serves tools and data to any agent, like LSP for editors.

An Agent Skill is a folder with a SKILL.md file: YAML frontmatter with a name and a description, then instructions, plus any references and scripts it needs. The trick is progressive disclosure. Only the name and description sit in the system prompt, at about 100 tokens per Skill; the body loads when a request matches the description; bundled files load only when read, and a script's code never enters the context, only its output. So the description is the trigger, and it must say what the Skill does and when to use it. This repository is a live example: the deck you are looking at was produced by the generate-presentation Skill in .claude/skills. Skills run in Claude Code from .claude/skills, on the Claude API in the code-execution container through the Skills API, and in claude.ai. Use Skills only from trusted sources and audit them like software, because a Skill can direct the agent to run code. The ticket-triage Skill on the right is the kind you write in Lab 03, turning a prompt you keep pasting into a reusable Skill. Ask: which instructions do you paste into a chat every week?
Topic 4 · Agent Skills & OpenSpec agent design 30-min walkthrough

Write the agent's contract before its prompt: problem → spec → tools → roles → escalation

↔
Bridge: an OpenSpec is the design review you already run: requirements, an API contract, an authorisation model and a runbook. Write it first; the system prompt, the tool schemas, the escalation middleware and the tests all trace back to one of its lines.
OpenSpec, as this course uses it, is a short agent design document with five sections, in this order: the problem, the spec, the tool contracts, the role boundaries and the escalation rules. The order matters. Engineers new to agents start with the prompt; you start with what done looks like and what the agent must never do. Tool contracts carry a side-effect class: read-only lookups are cheap to allow, writes need approval. Role boundaries are the authorisation model, and escalation rules are the runbook for when the agent should stop and hand over. Every line becomes something testable later: a schema, a tool definition, a middleware rule, an eval case in Module 5. The bill is tokens times price times calls, so there are three families of lever. Budget first: count before you send, cap the output, and lower effort for narrow tasks, because reasoning tokens bill as output. The top bar is Module 1's UC-1 scenario with 400 reasoning tokens per ticket; the second is visible output only. Then cache: both providers cache a stable prefix, so put the instructions, tool definitions and examples first and the ticket last. A timestamp at the top breaks every hit, silently. The worked example assumes 700 of UC-1's 900 input tokens are shared: that caches on Claude Sonnet 5.5, whose minimum is 512 tokens, and takes the bill from 468 to about 241 dollars, plus a few cents of cache writes. It does not cache on GPT-6.1 Sol, whose minimum is 1,024 tokens: a real design consequence. Then batch what nobody is waiting for: UC-1 has a 2-second target, so it cannot batch, but UC-3's overnight extraction can. Prices are list prices on 27 October 2026. Topic 5 · Cost optimisation & observability basics

Trace every round trip, and retry only what is safe to retry

FailureWhat you seeWhat your code does
Rate limit, overload, timeout, 5xxRateLimitError, APITimeoutError, InternalServerError; Claude also OverloadedErrorBack off and retry. Both SDKs already retry twice (max_retries), then queue or fail over
Bad requestBadRequestError (400): a wrong field or an unsupported parameterNever retry. Log the request ID and fix the code
Stopped short or declinedOpenAI status="incomplete" or a refusal item; Claude stop_reason max_tokens or refusalDo not parse. Route it, or retry once with a larger cap
Valid call, wrong outputA Pydantic ValidationError, or an unknown KB IDRe-ask once with the error message, then hand to a human
Tracing an LLM application is distributed tracing with two new attributes: tokens and the prompt version. Each model call, tool call and validation step is a span; the root span is one ticket. This waterfall is illustrative, but its shape is typical: the latency is in the model calls, and a retry hides inside what looks like one slow request. Log the request ID from both SDKs (response._request_id) so the provider's support team can find the call. For error handling, sort failures by whether a retry can help. Rate limits, overloads and timeouts are transient, and both SDKs already retry them twice with backoff. A 400 is your bug, so retrying just burns quota. A refusal or truncation is a valid response you must not parse. A schema-valid but wrong answer is a business-logic failure. LangSmith switches on with LANGSMITH_TRACING and a key in .env, then @traceable on your functions or wrap_openai and wrap_anthropic around the clients; Module 5 adds Langfuse and dashboards. Ask: does your current retry policy know the difference between a 429 and a 400?
Topic 6 · LangChain architecture & tool integration

LangChain gives you two shapes: a fixed chain, or an agent loop

Outline termWhat you use in LangChain 1.4Note

LangChain is a library of interchangeable parts with one interface: every prompt, model, parser and retriever is a Runnable with invoke, stream and batch, and the pipe operator composes them. That is the chain shape: you fix the steps, and it is the right choice for triage without tools. The agent shape is the loop you hand-wrote on slide 7, packaged: create_agent builds a small LangGraph graph with a model node and a tools node, and the model decides when to stop. Middleware is where your engineering goes: trimming and summarising before the model call, retries and limits around tool calls. The outline says "agent executors"; in LangChain 1.x that is create_agent, and AgentExecutor survives only in langchain-classic for old code. Provider choice is a configuration value: the labs' get_chat_model reads LLM_PROVIDER, so one notebook runs on either SDK. Module 4 opens up LangGraph itself. Topic 6 · LangChain architecture & tool integration

Tools are where the agent touches your estate: scope each one like a public API

# A provider-configurable, tool-enabled agent · LangChain 1.4 from langchain.agents import create_agent from langchain.tools import tool from langchain_tavily import TavilySearch # db: a read-only sqlite3 connection to the ops DB, row_factory=sqlite3.Row @tool def get_incident(incident_id: str) -> dict | None: """Fetch one incident by ID, such as INC-104233. Read-only.""" row = db.execute("SELECT id, title, priority, team, status " "FROM incidents WHERE id = ?", (incident_id,)).fetchone() return dict(row) if row else None agent = create_agent(get_chat_model(), # LLM_PROVIDER picks the SDK tools=[get_incident, TavilySearch(max_results=3)], system_prompt=TRIAGE_PROMPT) agent.invoke({"messages": [{"role": "user", "content": "Triage INC-104233"}]})
Common trap: a tool that returns a whole web page or table floods the context and hands the model untrusted instructions. Return the few fields you need, cap the rows, and treat every result as data.
From the agent's side every tool is the same thing: a name, a docstring and a typed signature, which LangChain's @tool decorator turns into the schema you wrote by hand on slide 7. The docstring is a prompt, so say what the tool does, what an ID looks like and that it is read-only. From your side the four kinds differ in risk. Search brings back untrusted text, which is how indirect prompt injection gets in; Module 5 defends against it. API tools need timeouts and should return a handful of fields, not the payload. Database tools get a read-only connection and parameterised, allow-listed queries; LangChain's SQLDatabase toolkit can write SQL for you, which is powerful and needs exactly those limits. Code execution has the largest blast radius, so it runs only in a sandbox. In Lab 04 you build a web search, database and summarisation agent that runs on either provider, with a mock search tool when no Tavily key is set. Topic 7 · Memory, context & session management

Memory is a policy for what you resend

# LangChain 1.4: memory is a checkpointer plus middleware on create_agent from langchain.agents.middleware import SummarizationMiddleware from langgraph.checkpoint.memory import InMemorySaver agent = create_agent(get_chat_model(), tools=tools, checkpointer=InMemorySaver(), # buffer: the thread keeps every message middleware=[SummarizationMiddleware( # summary: compress the older turns model=get_chat_model(small=True), trigger=("tokens", 4000), keep=("messages", 20))]) # window: a @before_model middleware that trims the history to the last k messages agent.invoke({"messages": [msg]}, {"configurable": {"thread_id": "INC-104233"}})
The model remembers nothing between calls; "memory" is the policy for what you resend. Buffer memory resends everything: perfect recall, but the cost and latency of every request grow with the conversation. Window memory resends the last k turns: flat cost, but it forgets, and here the incident ID from turn one falls out, so the agent asks again. Summary memory folds older turns into a summary written by a cheap model: bounded and mostly faithful, but lossy, and the summariser decides what was important. The chart is illustrative; in Lab 04 you measure buffer against summary on a multi-turn support scenario. The outline's names are the classic LangChain memory classes, which are now legacy in langchain-classic. In LangChain 1.4 a checkpointer gives the thread its full history, SummarizationMiddleware compresses it, and a before_model middleware trims it. The thread_id is the session key. Topic 7 · Memory, context & session management

Design the conversation as a workflow, with the session as its state

One thread per incident

Key thread_id on the incident, not the user, so two incidents never share a history.

Facts in state, not in prose

Slots such as incident_id survive summarising and trimming; chat text does not.

Stable first, volatile last

System prompt and tools at the front keep the cache warm; the new turn goes at the end.

Expire and isolate sessions

A session holds ticket text and personal data: time-box it, and never load another user's thread.

Open-ended chat is the hardest thing to test, so do not build one. Design the conversation as a small workflow: intake collects the slots, triage produces the structured record, lookup and proposal try a fix, and the conversation ends as resolved or escalated. Each step has an exit condition you can test, and P1 skips straight to a human. The session is that workflow's state: the slots, the current step and the message history, keyed by thread_id. Keeping facts in typed slots matters because summaries and trimming lose prose, while state survives. When you assemble each request, put the stable parts first for the cache and the volatile parts last. In Module 4 this sketch becomes a LangGraph state machine with checkpoints and human approval. Ask: what should happen to a session when the incident is closed?
Topic 8 · Agent architecture blueprint

The Enterprise Operations Assistant: triage → knowledge lookup → structured escalation

① History growth

Every turn resends the thread. Summarise, and keep one thread per incident.

② Raw tool output

A search page or a whole KB article floods the window. Return the top hits and the fields you need.

③ Serial round trips

Each tool hop is another model call. Cap the calls, and let one tool answer one question.

④ A drifting prefix

An edited prompt or reordered tools misses the cache on every call. Freeze and version them.

Wrap-up

Key takeaways, and a quick self-check

01Prompts are code

Template and version them, read the rendered request, and score every change on a labelled set.

02Schema for shape, code for truth

Constrained decoding guarantees valid JSON. IDs and business rules are checked in your code.

03The model asks; your code acts

Tool calls are RPC requests: validate the arguments, execute, and return the result with its ID.

04Specify before you prompt

Spec the tools, roles and escalation rules first; package repeated procedures as Skills.

05Cache, batch, trace

Stable prefix first, batch what can wait, log tokens per call, and retry only transient errors.

06Memory is a resend policy

Buffer, window or summary; keep facts in session state, one thread per incident.
